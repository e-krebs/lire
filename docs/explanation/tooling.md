# Tooling

Why the lint, format and check toolchain is shaped the way it is. Which command runs what is in
[../how-to/run-the-tests.md](../how-to/run-the-tests.md); the rules the custom lint plugins
enforce are written out in [../reference/conventions.md](../reference/conventions.md) and
[../reference/testing.md](../reference/testing.md).

## The oxc toolchain

Lire lints with **oxlint** and formats with **oxfmt**, both from the [oxc](https://oxc.rs)
project, instead of ESLint and Prettier. One fast pass covers the TypeScript, unicorn, oxc, React,
React hooks, jsx-a11y and Vitest rules, and `oxlint-tsgolint` adds type-aware rules to the same
pass (`options.typeAware` in [.oxlintrc.json](../../.oxlintrc.json)). The type-aware set is
mostly the `no-unsafe-*` and `no-unnecessary-*` families, which catch the `any` that leaks in
from parsed JSON and the dead branches that a stricter type leaves behind.

The lint config also bans `../` imports in favor of the path aliases (`client/`, `server/`,
`shared/`, `test/`, `fixtures/`, `e2e/`), and lets a test import its parent folder and nothing
higher. Imports then read the same from any depth, and a move does not ripple through relative
paths.

The [oxlint-tailwindcss](https://oxlint-tailwindcss.pages.dev) plugin lints the class names in
`src/client`. It reads the design system from [styles.css](../../src/client/styles.css), so it knows
the project's own tokens, and every rule it enables is an error. Most rules autofix with
`yarn fix`. The ones that do not are `prefer-scale-token`, which asks for `h-3.5` where `h-[14px]`
sets the same length at a 16px root font size, and `no-unknown-classes`. A size that must stay in
pixels, such as the text-card padding that `textHeight.ts` measures, opts out of the former. A string that is not a class list, such as a
variable named `style`, takes an `oxlint-disable-next-line` comment.

The service worker, [sw.ts](../../src/client/sw.ts), is the one client file lint ignores: it
typechecks on its own with the `WebWorker` lib (`yarn typecheck:sw`) and is left out of the SPA
project.

[.oxfmtrc.json](../../.oxfmtrc.json) sets a 100-column print width and leaves Markdown, CSS,
HTML, `package.json` and the generated route tree alone. The route tree is regenerated by the
router plugin, so formatting it would only produce churn. Prose in Markdown is wrapped by hand.

## Custom lint plugins

Two local jsPlugins in [scripts/oxlint/](../../scripts/oxlint/) turn repo conventions into lint
errors, so a convention holds without a reviewer remembering it:

- [code-conventions.js](../../scripts/oxlint/code-conventions.js): files in `src/client/hooks`
  are named `useXxx` (helpers go in `hooks/utils`), a function holds no lowercase render helper
  that returns JSX, and an `index.ts` that would re-export a single value holds that code in
  `index.tsx` instead.
- [test-conventions.js](../../scripts/oxlint/test-conventions.js): nested `describe` titles
  start with "when", and `screen`, `within` or `page` queries sit inside a getter or method of a
  `ui` object.

[code-conventions.js](../../scripts/oxlint/code-conventions.js) also holds `no-raw-jsx-text`, an
error in `src/client`. It flags JSX text containing a letter, a string or template literal directly
inside JSX, and a literal on `aria-label`, `title`, `placeholder`, `alt`, `label` or `data-tip`,
because UI text belongs in the i18n catalog ([conventions](../reference/conventions.md#ui-strings)).
The brand name `Lire` is allowed. Tests, stories and `routes/dev.*.tsx` are exempt. A string built
in plain code, such as an object-literal `aria-label`, is outside the rule and left to review.

The config adds Vitest rules beside them: `vi.mock` and its relatives, and `vi.spyOn`, are
banned in tests, because tests go through MSW and real modules instead. Each lint message names
the doc that explains its rule, so the error itself points at the reasoning.

## knip

[knip](../../knip.json) finds unused files, exports and dependencies. It runs twice in CI:
`yarn knip` over the whole project, and `yarn knip:production` over production code only, so an
export used only by a test still counts as dead in the shipped app. The route tree is the entry,
since every route is reached from it; test helpers and stories are kept out of the production
project.

## Gates in scripts/

Node scripts guard what lint and types cannot see. Each one exits non-zero on a hit. CI runs the
build, export coverage and access gates in its `verify`, `preflight` and `check-live` jobs, the
link gate in its own `docs-links` job and the story gate in the `storybook` job
([ci.yml](../../.github/workflows/ci.yml)).

### check-links

[check-links.ts](../../scripts/check-links.ts) checks every relative link and heading anchor in
the repo's Markdown, tracked or not, while it skips gitignored files. A doc set that cross-links
instead of repeating itself depends on those links, and a renamed heading breaks an anchor
without any other signal. The script fails loudly on link-shaped text it cannot parse, and on an
unclosed fence, rather than quietly checking less. GitHub-style line fragments such as `#L42`
are accepted as is. CI runs it in the `docs-links` job on every run, whatever changed.

### check-dist-secrets

[check-dist-secrets.ts](../../scripts/check-dist-secrets.ts) runs after a build. It fails when:

- git tracks an env file other than `.env.sample`, since `.gitignore` alone keeps them out and a
  mistyped pattern fails silently;
- a `VITE_` env var has a secret-shaped name, because Vite would inline it into the bundle;
- `dist/` contains a named secret such as `NEWSBLUR_PASSWORD` or `NEWSBLUR_OAUTH_CLIENT_SECRET`, or a secret-key pattern;
- in a real build (`VITE_API_MODE=real`), a JS chunk still carries seed fixture markers, which
  would mean the fixture transport was not dropped.

The patterns are named rather than a bare match on "secret", because React's own bundle ships
strings with that word in them. CI runs it after the default build, the real build and the demo
build, and the SPA and demo deploy scripts run it before they upload (`deploy:storybook` does not, because the script scans `dist/` only and the Storybook build lands in `storybook-static/`; Storybook also carries no `VITE_` secrets, so the secret gate has nothing to check there).

### check-demo-brand

[check-demo-brand.ts](../../scripts/check-demo-brand.ts) runs on the demo build. The demo is
public, so on a machine that holds a recording it fails on the recorded profile id or email in
`dist/`. The recording is gitignored, so the check only applies locally and checks nothing in CI.

The script takes an optional directory argument and defaults to `dist`. `yarn check:demo
storybook-static` scans the Storybook build, which is public too: the `storybook` CI job runs it
after `yarn build:storybook`, and `deploy:storybook` runs it before the upload.

### check-access, provision-pages and check-live

Three scripts run against Cloudflare in CI before and after the deploys. They call the REST API
with `fetch`, read `ACCESS_AUD` and `ACCESS_TEAM_DOMAIN` from [wrangler.toml](../../wrangler.toml),
and share hostnames and project names from [deploy-targets.ts](../../scripts/deploy-targets.ts).
check-access and provision-pages exit `1` with a message when an env var is unset, and check-live needs none.

- [check-access.ts](../../scripts/check-access.ts) fails when the Access application does not
  match wrangler.toml, when a policy's decision is not `allow` (a `bypass` or `non_identity` policy
  would open the host), when the policy emails differ from `ACCESS_ALLOWED_EMAIL`, or when that
  pin is unset.
- [provision-pages.ts](../../scripts/provision-pages.ts) only creates: missing Pages projects,
  custom domains and DNS records. It fails on a DNS record that points elsewhere or is not
  proxied, since the Worker route fires only on a proxied record, and on a `lire` project whose
  subdomain is not `lire-6s2.pages.dev`, since a new pages.dev host would sit outside Access.
- [check-live.ts](../../scripts/check-live.ts) requests every host and expects an Access redirect
  on the protected ones and a plain answer on the public ones. It retries for about a minute,
  because Pages and DNS changes take time to reach the edge.

### check-export-coverage

[check-export-coverage.ts](../../scripts/check-export-coverage.ts) reads the client and server
coverage reports and fails on any exported top-level function that no test calls. Line coverage
can stay high while a whole export goes untested; this gate makes "every export is called by a
test" a hard rule. It runs after `yarn test:coverage` and `yarn test:worker:coverage`, whose
reports it reads.

### check-stories

[check-story-order.ts](../../scripts/check-story-order.ts) (`yarn check:stories`) reads the inline
`storySort` order in [preview.tsx](../../.storybook/preview.tsx) as text and walks every
`src/**/__stories__/*.stories.tsx`. A story must sit in
`src/client/components/<root>/<group>/__stories__/`, with kebab-case folder names, and its title
must equal the sentence-case root, the sentence-case group and the file name, so the title is the
folder path. Every story root and group must appear in the order list, every listed root and group
must hold a story, and no two titles are equal.

Storybook's own sort cannot catch this. It keeps a title that the order list does not name and
places it after the listed ones, so a typo in a title moves the story down the sidebar and
nothing fails. The order has to be a literal in `preview.tsx`, because Storybook rejects an
imported one, which is why the script parses the file instead of importing it. A group with no
story stays out of the list, as `Feedback` does until it gets one.

## Where CI runs what

The `docs-links` job runs the link gate on every run. The `verify` job runs `yarn dedupe --check`, lint, both knip passes, the format
check, the five typecheck projects, both coverage runs and the export coverage gate. Then it
builds three times, default, real and demo, and runs the secret gate after each and the demo
gate after the demo build. The `e2e` and `storybook` jobs run the browser tests, and the
`storybook` job also runs the demo gate on `storybook-static` and the story order gate. The
`cloudflare-gate` job runs only on `main` and checks that the Cloudflare secrets exist. The
`preflight` job then runs `check-access` and `provision-pages`. The deploy jobs for the SPA, demo,
Storybook and Worker follow once their dependencies pass, and `check-live` runs after all four.
Every job that installs dependencies uses the shared [setup action](../../.github/actions/setup/action.yml),
which restores the Yarn cache. The `e2e` and `storybook` jobs run in the official Playwright
container image, which ships the browsers and their system libraries. The runner then installs
nothing with apt and downloads no browser, because a slow install once held the `e2e` job for 14
minutes and a hung `install-deps` timed out other runs. The image tag names the Playwright version,
so it must match `playwright-core` in `yarn.lock`: a mismatch fails the job with a missing browser
executable. Every job sets `timeout-minutes`, about three times its normal duration, so a hung
step fails in minutes. Playwright's `globalTimeout` ends a stuck run before the job limit, so the
report still uploads. Every Cloudflare job is skipped when the gate finds no secrets. [ADR 0006](../adr/0006-ci-owns-cloudflare-setup.md)
records why CI owns this setup.

## Change-based gating

A `changes` job decides which checks and deploys a push needs. Each area (app, Storybook, Worker,
tooling, infra) is an inclusion list: a job runs only for files it ships or depends on, so a docs
or Android change deploys nothing. Inclusion lists alone fail closed in the wrong direction, since
a new file nobody listed would skip a deploy. A catch-all `unknown` filter matches any changed file
that no area list and no ignore list names, and turns every area on. A manual run does the same.
The cost is a full run for an unclassified file; the gain is that a deploy is never skipped by
mistake. [deploy.md](../how-to/deploy.md) has the area table.

## Dependency updates

[dependabot.yml](../../.github/dependabot.yml) opens a weekly PR for the npm packages and one for
the GitHub Actions. The npm PR groups minor and patch updates. A major update gets its own PR. Each
PR runs the full CI, so the gates above decide whether it is safe to merge. Nothing merges on its
own.

Dependabot resolves the lockfile on its own and never deduplicates it, so the `yarn dedupe --check`
gate would fail on most npm PRs. [dependabot-dedupe.yml](../../.github/workflows/dependabot-dedupe.yml)
runs `yarn dedupe` on each Dependabot PR that changes `yarn.lock` and pushes the result as a
commit. The push uses a personal access token stored as the `DEPENDABOT_DEDUPE_TOKEN` Dependabot
secret, because a push made with the default token starts no CI run. The workflow skips any run
whose actor is not Dependabot, so its own push does not loop.
